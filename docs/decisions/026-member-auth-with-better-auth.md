# Member Authentication with Better Auth

Date: 2026-10-28

Status: proposed

## Context

AvyWeb is becoming AvyApp's backend and the consumer identity provider for the Avy platform (see the *AvyApp Notifications Backend* design). That needs public accounts — **Members** — separate from staff **Users**, who sign into the admin under the RBAC model ([004](004-rbac.md), [012](012-non-rbac-access-patterns.md)). Members need anonymous accounts tied to an AvyApp device that can later be linked to email or social sign-in, and must work from AvyWeb (cookies, one host per tenant) and AvyApp (Expo).

Payload's built-in auth covers email/password and API keys, not anonymous accounts, OTP or social sign-in. Better Auth covers all of them (`anonymous`, `emailOtp`, social providers, `@better-auth/expo`), and Payload supports custom auth strategies per collection.

Constraints that shaped the decision:

- Production tenants are on separate registrable domains (`nwac.us`, `sierraavalanchecenter.org`, …), so browsers can't share one auth cookie across them, and a single cross-site auth origin is blocked by Safari ITP.
- All auth collections' strategies run in one list on every request, and `req.user` holds one user. Since [025](025-admin-served-only-from-the-apex.md) the admin session only exists on the apex, so a User and a Member session can only meet there.
- The database is SQLite/Turso ([002](002-sqlite-turso.md)); Payload's SQLite dev push diffs the live schema, and Turso ignores FK pragmas inside transactions.
- The only maintained Payload/Better Auth integration, `payload-auth`, assumes the Better Auth user collection is `admin.user` and replaces the admin login, and is tested only on Postgres.

## Decision

- **A new `members` auth collection**, distinct from `users`, with `disableLocalStrategy: true` and one custom strategy that resolves a Better Auth session to the Member. The strategy short-circuits when no Better Auth cookie is present and runs after Payload's own JWT strategy, so an admin session always wins on admin and API routes. Public pages read the Member through Better Auth's `getSession`, not `req.user`.
- **Hybrid table ownership.** Payload owns `members` as a collection; Better Auth's `user` model is mapped onto it. Better Auth's `session`, `account`, `verification` and `rateLimit` tables are Drizzle tables (generated by the Better Auth CLI) injected through `beforeSchemaInit`, so Payload migrations are the only migration system. Better Auth uses its Drizzle adapter on `payload.db.drizzle`. `payload-auth` is not used.
- **Anonymous Members are device-bound and created lazily** by AvyApp on the first action that needs an identity. A custom Better Auth endpoint `/sign-in/device` exchanges a random device secret (hashed on the `Device`) for a session, and only while the Member is still anonymous. Linking happens in `onLinkAccount`: Devices, Subscriptions and Deliveries move to the Linked Member, Subscriptions are unioned, and the Anonymous Member is deleted.
- **Auth is served on each tenant's own host** (`baseURL.allowedHosts` from the hardcoded center list, [013](013-hardcoded-tenant-lookup.md)). One account, signed in per site; no cross-site single sign-on. Google redirect URIs are registered per tenant domain. AvyApp talks to the apex and uses native Google (and later Apple) sign-in with `idToken`s.
- **Members and Users never link**, even with the same email.
- **Sessions** are 60-day rolling; **rate limits** are stored in the database; **OTP email** is Avy-branded via Payload's email adapter.
- **Account deletion** uses Better Auth's `deleteUser` with a hook that deletes the Member's Payload rows explicitly rather than relying on FK cascades.

## Consequences

- Better Auth writes to `members` bypass Payload hooks and validation. Side effects belong in Better Auth `databaseHooks`; Payload hooks on `members` only fire for admin edits.
- The Better Auth schema must be regenerated and re-injected when Better Auth plugins change, and its generated file must import Payload's Drizzle re-export to avoid a version mismatch.
- A Member who uses several center sites signs in on each. Revisiting that means a central auth domain plus a code-exchange redirect, not shared cookies.
- Member sessions put a session cookie back on center hosts, which [025](025-admin-served-only-from-the-apex.md) deliberately emptied. A form-embed script ([017](017-form-embeds-in-page.md)) on a center page can make same-origin calls as the signed-in Member. The cookie is `httpOnly`, so the script can't read it, and Member data is low-sensitivity (notification preferences, feed), but destructive or identity-changing actions (account deletion, email change) should require a fresh session or a re-sent OTP.
- On Android, reinstalling the app loses SecureStore and therefore the device secret, so an unlinked reinstall starts a new Anonymous Member. iOS Keychain survives reinstall.
- Every tenant domain added to the center list also needs adding to Google's redirect URIs (and Apple's, later).
- This depends on a POC (spec in the monorepo at `.scratch/avy-app-notifications/poc-1-better-auth-members.md`) confirming the hybrid tables work on SQLite/libsql. If they don't, the fallback is Better Auth writing through Payload's Local API (e.g. `payload-auth`'s standalone adapter), and this ADR is revised.
